Reviewer stance: assume incomplete and wrong until verified against source.

### B1. The `#326` claim is false against the code — the bug is already fixed

**Location:** `finance-security-layers`, "Two adjacent open finance issues", line 776-779.
Repeated implicitly nowhere else.

**Doc says:** "`plaid-exchange` logs the full Plaid exchange response on an

**Evidence:** `ConjureOS/supabase/functions/plaid-exchange/index.ts:130-140`

The remediation named in the issue body ("log only safe scalars, e.g.

**and** `origin/main` (`git diff origin/main origin/dev -- supabase/functions/plaid-exchange`

**Why this is a blocker, not a nit.** This is the highest-stakes section of a
finance doc, and the doc explicitly claims it "verified against the ConjureOS

"live banking credential in logs, MAJOR" and spends a session re-fixing a fixed

the claims that matter.

### B2. The entire live-data restart plan is unimplementable as written: a store-installed anchor app cannot get a Supabase JWT

**Location:** `finance-restart-checklist` step 5 (lines 315-325) + `finance-architecture`
host-integration bullet (lines 400-401). The doc states both facts and never
connects them.

**Doc says (step 5):** "Build a `RestFinanceApi` that maps `finance-read`'s
`{accounts, transactions}` onto `src/api/types.ts` … and fill in
`PlaidBankProvider` … against `plaid-link-token` → `plaid-exchange` → `plaid-sync`
→ `plaid-unlink`."

**Doc says (architecture):** "`auth.getUser` / `auth.getAccessToken` —
**built-in/default apps only**."

**Evidence that these are incompatible:**

- Every finance edge function requires the caller's user JWT and 401s without it:
  `ConjureOS/supabase/functions/finance-read/index.ts:41-51`
  (`missing_authorization_header` → `not_signed_in`), same guard at
  `plaid-sync/index.ts:108-111`.
- The kernel returns **null**, not a token, for any app whose path is not in the
  built-in set: `ConjureOS/src/kernel/index.ts:1967-1969`
  — `if (!BUILT_IN_APP_PATHS.has(this.currentApp)) { return { ok: true, result: null }; }`
- `BUILT_IN_APP_PATHS` is derived from `DEFAULT_APPS`
  (`ConjureOS/src/kernel/index.ts:99-101`), whose slugs are
  `lifeos-docs, security-test, dev-docs, report-issue, help-desk-ticket,
  conjure-chat, calculator, jump-runner, icon-generator`
  (`ConjureOS/src/kernel/defaultApps.ts`). **`finance` is not among them** — it is
  a store-installed anchor app at `/apps/finance`.
- The app's own token accessor therefore always yields null in production:
  `conjureos-finance/src/platform/host.ts:90-98` (`getHostAccessToken` →
  `b.auth.getAccessToken()`), which `src/api/index.ts:37` wires in as the default
  for the synced path.

So on the day someone finishes `RestFinanceApi`, every call returns
`unauthorized`. Fixing it is not a line of app code — it is a **ConjureOS kernel
decision**: promote finance into `DEFAULT_APPS` (which changes its distribution
model and its security posture — built-ins get the raw user JWT, gated for exactly
this reason per `SECURITY.md` I1/I2), or design a new scoped-token capability, or
proxy finance reads through a bridge that never hands the app a token. That is
architecture work in the *other* repo, and the doc's "biggest piece of actual
work" estimate silently excludes it.

**Should say:** a first-class known gap and a step 4.5 in the restart checklist —
"Decide how the app authenticates to `finance-read`. As a store-installed app,
`auth.getAccessToken` returns null (`kernel/index.ts:1967`, gated on
`BUILT_IN_APP_PATHS` from `DEFAULT_APPS`); `finance` is not a default app. Options:
(a) make finance a built-in, (b) add a scoped finance token capability to the
kernel, (c) route reads through a host bridge. **Nothing downstream works until
this is chosen.**"

## ENCRYPTION SECTION — PASS, NO OVERSTATEMENT FOUND

I tried hard to find an overstatement here and could not. Verified line by line
against source:

- "NOT end-to-end" — stated four times, including "the product must not claim that
  it is." Matches `fieldCrypto.ts:1-9`, `088_finance_field_encryption.sql:9-10`,
  `DECISIONS_ARCHIVE.md:71` (2026-06-24) and the 2026-05-28 abandonment decision
  (`DECISIONS_ARCHIVE.md` §2026-05-28, "Conjure Finance: server-side encryption at
  rest…"). Both dates the doc cites are correct.
- **Why true E2E is impossible** — "Plaid sync is *server-side*: the access token
  and `/transactions/sync` run in an edge function, so the server necessarily holds
  plaintext at the moment of ingest," plus the four consequences (webhook sync,
  server categorization, server recurring detection, cross-device sign-in). This is
  a faithful restatement of the 2026-05-28 decision, and it is true of the code
  (`plaid-sync/index.ts` holds plaintext between the Plaid fetch and `encryptField`).
- **Threat model** — "defends against an offline data-at-rest leak… does **not**
  defend against a fully compromised live server, because the server decrypts at
  runtime to serve the row's owner." Correct and appropriately narrow.
- **Mechanism** — AES-GCM-256 (`fieldCrypto.ts:63`), 12-byte random IV (`:25`, `:101`),
  envelope at `:104`, keyring `:66-90`, decrypt-by-keyId `:120`, encrypt-always-current
  `:100`, key-id regex + old≠current enforcement `:73`/`:82-83`, null-passthrough
  `:99`/`:111`. Every claim checks out, including the exact `FINANCE_DEK is not set
  on this function` string at `:71`.
- **Write/read paths** — accounts `plaid-sync/index.ts:201-217`, transactions
  `:307-323`, chokepoint `finance-read/index.ts:44-48` (anon client + caller JWT, no
  `service_role`), decrypt `:86-106`, fail-closed `:108-112`, limits 500/5000 `:34-35`.
- **Encrypted vs plaintext column lists** — exact match to `088:29-38` and the
  design comment `088:12-14`. "Idempotent, only alters a column whose type is not
  already `text`" matches `088:41-53`.
- **Consequence** — "amounts and balances are no longer SQL-aggregatable" matches
  `088:17-19`.
- **Rotation ordering + the destructive final step** — matches
  `FINANCE_ENCRYPTION.md` §"Rotate the key" and its idempotent/destructive tags.
- **"Losing the key with no backup is permanent, unrecoverable loss"** — matches
  `FINANCE_ENCRYPTION.md:60-71` + `OPEN_QUESTIONS.md:35`.

The one thing I would add for completeness (not a defect): layer 2's Vault
protection has a *different* custodian model — `vault.secrets` is encrypted with a
Supabase-managed root key, not `FINANCE_DEK` — so the "key is not in the database"
argument that holds for layer 3 does not transfer to layer 2 unchanged.
