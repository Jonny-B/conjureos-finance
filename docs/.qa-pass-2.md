**Location:** `finance-ci-publishing` (lines 1030–1182), `finance-known-gaps`,
`finance-reference-map`. The strings `#14`, `injection`, `release.body` appear
**nowhere** in 1,403 lines.

**Evidence** — `conjureos-finance/.github/workflows/publish-store.yml:65-79`
(`origin/dev`):

```yaml
      - name: Resolve changelog
        id: changelog
        run: |
          if [ "${{ github.event_name }}" = "release" ]; then
            text="${{ github.event.release.body }}"          # :69
            [ -z "$text" ] && text="${{ github.event.release.name }}"   # :70

```

`${{ }}` is substituted **into the script text** before the shell runs, so a
release body is shell source on a runner that holds `CONJUREOS_REPO_TOKEN` and
the publish credentials. Both sibling anchor repos already fixed exactly this:
`conjureos-app-recipes/.github/workflows/publish-store.yml` (`env: REL_BODY /
REL_NAME / REL_TAG / DISPATCH_CHANGELOG`, with a comment recording that a
release body reading *"I made this"* once failed the job with
`made: command not found`) and `conjureos-fitness`'s equivalent (`env:
RELEASE_BODY …`, "Same fix conjureos-app-recipes' workflow took, DECISIONS
2026-06-21"). Finance never got it. Issue #14 is **open**, labeled
`security`/`ci`, filed 2026-08-21.

**Why this is a blocker, not a nit.** The doc's `finance-ci-publishing` section
is a close read of this exact workflow — it discusses the PAT, the `html-path`
vs `source-path` input, and the composite action's arg assembly — and misses the
one line in it that is a security defect. Worse, it is *load-bearing for the
restart plan*: `finance-restart-checklist` step 9 and the bootstrap runbook's
step 4 both say "a published GitHub Release ships to **prod**". Point 2 of #14
is the one that will actually bite: any real changelog containing a backtick,
`"` or `$` breaks the prod publish, and the doc promises it will work.

**Should say:** in `finance-ci-publishing`, a third root cause beside the two
already there — "Root cause #3 (`conjureos-finance#14`): the changelog step
inlines `${{ github.event.release.body }}` into a `run:` block (`:69`, and
`:70`/`:71`/`:73`). That is GitHub's standard script-injection pattern *and* it
crashes on an ordinary backtick, so the release→prod path is unreliable until
fixed. Copy the recipes/fitness `env:` form verbatim." Plus a line in
`finance-known-gaps` and the reference-map row for `publish-store.yml`.

## SIGNIFICANT

### S1. "Secrets are read at invocation, so no redeploy is needed" is wrong where it matters most — the prod switch-on

**Location:** `finance-restart-checklist` step 3, lines 442–444.

**Evidence.** `_shared/fieldCrypto.ts:66-89` memoizes the keyring in a
module-level `let keyringPromise`, guarded by `if (!keyringPromise)`. The promise
is assigned **before** it can reject (`:69`), so a **rejected** keyring is cached
for the isolate's whole life. Prod today has no `FINANCE_DEK` (`:70-71` throws
`FINANCE_DEK is not set on this function`). Sequence a restarter will actually
hit: call the function → rejection cached → `supabase secrets set` → call again →
**same** `FINANCE_DEK is not set` error, from the warm isolate, with the secret
correctly set. They will conclude the secret did not take.

The doc inherited the sentence from `FINANCE_ENCRYPTION.md:57-58`, which
contradicts itself four lines later: its rotation steps 2 and 5 both end with
`# redeploy` (`FINANCE_ENCRYPTION.md:120`, `:140`). The doc's own mechanism
bullet (line 854) already says the keyring is "memoized per isolate" — the two
statements are never reconciled.

**Should say:** step 3 — "*Expected output:* `Finished supabase secrets set.`
**Then redeploy the finance functions** (or wait for isolate recycle): the
keyring is memoized per isolate and a *failed* keyring is cached too
(`fieldCrypto.ts:66-89`), so a warm isolate keeps returning `FINANCE_DEK is not
set` after the secret exists. `FINANCE_ENCRYPTION.md:57-58` says no redeploy is
needed; its own rotation steps `:120`/`:140` redeploy. Trust the redeploy."

### S3. The rotation runbook's step 3 is pseudocode, and gap 6 will abort it

**Location:** `finance-field-encryption` → "Rotation and recovery", lines 885–892
("read `FINANCE_ENCRYPTION.md`. It is the operator runbook and it tags every step
idempotent vs destructive").

That is true and the ordering the doc summarizes is right. What the doc does not
say is that the middle step has no tool. `FINANCE_ENCRYPTION.md:143-171` is
headed "Re-encrypt script (step 3)" and its body reads
`// finance-reencrypt.mjs — bundle fieldCrypto.ts with esbuild first, or run via
a Deno runtime. **Pseudocode of the loop**`. No such script exists in the repo
(`git ls-tree -r origin/dev` — nothing matching `reencrypt`). Two further traps
in that pseudocode:

- it selects with no pagination (`:161`), so PostgREST's default 1000-row cap
  silently re-encrypts only the first page — step 4's `like 'v1.%'` verify is
  what saves you;
- it calls `decryptField(row[c])` over **`user_category`** (`:157`), which is the
  one column a client can write plaintext into (gap 6). One plaintext value and
  the rotation loop throws mid-run.

**Should say:** in the rotation paragraph — "Step 3 of that runbook is
**pseudocode, not a script**; you will write `finance-reencrypt.mjs` yourself
(add pagination — the sketch has none). And fix gap 6 first: a single plaintext
`user_category` makes the re-encrypt loop throw part-way through."

### S4. Option (b) is the right recommendation, but the doc omits what it costs

**Location:** `finance-restart-checklist` step 5, option (b), lines 474–482.

The precedent is real and quoted accurately — `recipes-db/index.ts:1-21` reads
exactly as described, and `PHASE_36_DESIGN.md:47` (invariant I2) explicitly
blesses "audience-scoped minted tokens (`mint-app-token`)" as the sanctioned way
apps reach a backend. So the recommendation stands.

What is missing is the trade. `recipes-db/index.ts:9-10` and `:19-21`: it
verifies the minted token in-process, **runs as the service role** (RLS
bypassed, ownership enforced by `creator_id`), and is deployed
`verify_jwt = false`. Adopting that shape for `finance-read` **replaces** the
property the doc advertises three sections earlier as a security feature —
"reads **only their rows through an RLS-scoped anon client — no `service_role`**"
(`finance-read/index.ts:44-48`, doc line 862). Per-user isolation would move
from Postgres RLS to a hand-written `eq("user_id", sub)`, in the one function
that decrypts bank data.

**Should say:** add to (b) — "Cost: `recipes-db` runs `verify_jwt=false` +
service role with ownership enforced in-process. Applying that to `finance-read`
gives up its RLS-scoped-anon-client least-privilege property (`:44-48`) and moves
isolation into application code. Acceptable, but it is a real change to layer F2
and must be recorded, not inherited by accident."

### S5. The encryption section never says two whole tables are unencrypted

**Location:** `finance-field-encryption` → "Deliberately plaintext", lines 871–874;
`finance-known-gaps` item 7.

The plaintext list is scoped to columns *within* `transactions` and `accounts`
("ids, `plaid_*_id`, dates, `iso_currency_code`, `pending`, `payment_channel`,
`mask`, `type`/`subtype`"), which reads as "everything sensitive is covered."
Migration 088 touches only those two tables (`088:29-38`). Not covered:

- **`finance.budgets`** — `category` + `amount numeric(18,2)` (`035:173`), and
  the client has `grant select, insert, update, delete` on it (`035:188`). Gap 7
  names this but only as "record the decision explicitly"; the *implication* — a
  stolen dump yields the user's category-by-category budget profile in the clear
  — is never stated in the threat model.
- **`finance.recurring`** — `merchant_name text` **plaintext** (`035:199`) and
  `average_amount numeric(18,2)` (`035:200`). `merchant_name` is the same data
  class the whole layer exists to protect, and it is named **nowhere** in the
  doc. Gap 8 correctly says nothing populates the table today; the moment
  someone does ("either populate it or drop it"), they silently write plaintext
  merchant names beside encrypted ones.

One length-leak note for completeness while in the threat model: AES-GCM is
unpadded, so ciphertext length reveals plaintext length — digit-count of an
amount, character-count of a merchant name — in exactly the offline-dump
scenario the layer defends against. Minor, but it belongs in a section that
states its threat model "plainly".

**Should say:** in "Deliberately plaintext", add "**and two entire tables**:
`finance.budgets` (`amount`, `category`; client-CRUD'd, `035:169-188`) and
`finance.recurring` (`merchant_name` **plaintext**, `average_amount`;
`035:195-217`). A dump leaks the budget profile today, and would leak merchant
names the day anything populates `recurring` — decide that *before* gap 8 gets
closed by populating it."
